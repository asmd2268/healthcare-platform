# دليل تشغيل الاشتراكات خطوة بخطوة

> دليل داخلي يشرح كيف نقسم الاشتراكات ونفعلها ونجددها ونوقفها. لا تُستخدم
> مفاتيح `service_role` في المتصفح أو البريد أو نظام CRM، ولا تُجرى عمليات
> الإنتاج يدويًا من جهاز شخصي.

## 1. نموذج الاشتراك

الاشتراك عقد تجاري وسجل تشغيلي وترخيص تقني؛ وهذه أشياء مترابطة وليست شيئًا
واحدًا:

1. **العرض/نموذج الطلب:** السعر والمدة والنطاق والالتزامات.
2. **الفوترة والتحصيل:** النظام المالي المرجعي للمبالغ والضريبة وحالة الدفع.
3. **الترخيص:** ما تسمح المنصة بعرضه على الخادم، في نطاق محدد ومدة محددة.
4. **الصلاحيات وRLS:** ما يستطيع المستخدم فعله داخل النطاق بعد نجاح الترخيص.

الدفع لا يمنح صلاحية مباشرة، والترخيص لا يتجاوز RBAC/RLS. عند التفعيل الصارم:

```text
الوصول الفعلي = وحدات نسخة النشر
             ∩ وحدات الترخيص النشط
             ∩ صلاحية المستخدم
             ∩ النطاق المسموح عبر RLS
```

## 2. وحدات البيع والنطاق

- المستأجر `tenant`: الحد الأعلى للعزل والعميل التجاري عادة.
- المنظمة `organization`: كيان قانوني/تشغيلي داخل العميل.
- المنشأة `facility`: مستشفى أو فرع أو موقع تشغيلي.
- المستخدم المسمى: شخص واحد؛ لا تباع حسابات مشتركة.
- الوحدة: مفتاح برمجي من القائمة المعتمدة، لا اسم تسويقي حر.

مفاتيح الوحدات الحالية:

`core`, `inventory`, `inspections`, `medication_errors`, `policies`, `capa`,
`reporting`, `administration`, `audit`.

لا تُضاف `core` إلى entitlement لأنها متاحة للدخول الآمن والإعدادات. يفضل أن
يكون الترخيص على مستوى `tenant` في SaaS العادي. استخدم مستوى المنظمة أو المنشأة
فقط عندما يكون العقد مختلفًا فعلًا، مع اختبار الوراثة وعدم وجود ترخيص أوسع
يتغلب عليه.

## 3. رموز الخطط الداخلية

| Plan code | الاستخدام | Deployment profile | Modules | الحالة الآن |
| --- | --- | --- | --- | --- |
| `INV-RO-PILOT` | تجربة قراءة المخزون 90 يومًا | `inventory` | `inventory`, `audit` | مسموح |
| `QLT-DP` | شريك تصميم الجودة | `quality` | حسب SOW، ولا يفعل إنتاجيًا | مشروع فقط |
| `MED-DP` | شريك تصميم سلامة الدواء | `medication-safety` | حسب SOW، ولا يفعل إنتاجيًا | مشروع فقط |
| `INV-GA` | اشتراك مخزون إنتاجي | `inventory` | `inventory`, `audit` | محجوب حتى GA |
| `QLT-GA` | اشتراك جودة إنتاجي | `quality` | `inspections`, `policies`, `capa`, `reporting`, `audit` | محجوب حتى GA |
| `MED-GA` | اشتراك سلامة دواء إنتاجي | `medication-safety` | `medication_errors`, `capa`, `reporting`, `audit` | محجوب حتى GA |
| `FULL-GA` | المنصة الإنتاجية | `full` | وحدات GA المتعاقد عليها فقط | محجوب حتى GA |
| `CUSTOM` | نشر/نطاق خاص | `custom` | allowlist معتمد | لجنة عرض وسلامة |

لا تنشئ plan code جديدًا في عقد منفرد. يحدث هذا الجدول أولًا، ثم التسعير، ثم
نسخة النشر، ثم اختبارات القبول.

## 4. سجل الاشتراك المرجعي

حتى يكتمل تكامل نظام مالي/CRM، يحتفظ مالك العمليات بسجل وصول مقيد يحتوي الأعمدة:

```text
customer_legal_name
tenant_id
organization_id
facility_id
plan_code
deployment_profile
hosting_mode
license_model
module_keys
white_label_enabled
max_users
max_facilities
contract_number
order_form_version
billing_customer_id
billing_subscription_id
invoice_number
payment_status
starts_at_utc
expires_at_utc
grace_ends_at_utc
renewal_notice_at_utc
commercial_license_id
license_revision
external_reference
owner
approval_ticket
acceptance_evidence_url
status
last_verified_at_utc
```

لا يحوي السجل كلمات مرور أو مفاتيح API أو بيانات بطاقات أو بيانات صحية. النظام
المالي هو المرجع للمبالغ، وقاعدة المنصة هي المرجع للترخيص، والعقد الموقع هو
المرجع للنطاق القانوني.

## 5. دورة الحالة

```text
lead -> qualified -> quoted -> signed -> awaiting_payment
     -> provisioning -> active -> renewal_due -> renewed
                                      |-> grace -> suspended
                                      |-> cancelled
                                      |-> expired
```

حالات قاعدة الترخيص نفسها هي: `draft`, `trial`, `active`, `suspended`,
`expired`, `cancelled`. لا توجد حالة `grace` مستقلة؛ السماح خلالها مشتق عندما
يبقى الترخيص `active` أو `trial` ويقع الوقت بعد `expires_at` وحتى
`grace_ends_at`.

السياسة الافتراضية:

- إشعار التجديد: قبل 90 ثم 60 ثم 30 يومًا.
- فترة السماح: 14 يومًا للاشتراك الإنتاجي، ولا تمدد التجربة تلقائيًا.
- التعليق: بعد انتهاء السماح أو حسب العقد، بموافقة مالك العمليات والمالية.
- الإلغاء: في نهاية المدة عادة؛ الإلغاء الفوري يحتاج مرجعًا تعاقديًا وموافقة.
- الاحتفاظ/التصدير/الحذف: حسب العقد وسياسة البيانات، لا حسب حالة الترخيص وحدها.

## 6. قبل توقيع العقد

1. أنشئ بطاقة الفرصة واستخدم أسئلة الاستكشاف في دليل البيع.
2. عيّن تصنيف الجاهزية لكل مطلب. أزل أي `HOLD` من النطاق أو حوله إلى بند مؤجل
   غير مسعّر وغير ملزم.
3. اختر `plan_code` وdeployment profile ونطاق الترخيص.
4. احسب السعر بالمعادلة والسياسة، وسجل كل خصم واعتماده.
5. أكمل مراجعة الأمن والخصوصية وموقع البيانات والتكاملات.
6. اكتب SOW: المشمول، المستبعد، مسؤوليات الطرفين، البيانات، التسليم والقبول.
7. اجعل العقد ونموذج الطلب والفاتورة متطابقة في الاسم والمدة والقيمة.
8. لا تعد بتاريخ تشغيل قبل اعتماد خطة التنفيذ والاعتماديات.

بوابة النجاح: عقد ونموذج طلب موقعان، حالة تحصيل تسمح بالتفعيل، تذكرة تهيئة،
مسؤول عميل، ونطاق بيانات معتمد.

## 7. التهيئة والتفعيل

### 7.1 تهيئة البيئة

1. أنشئ tenant/organization/facility بمعرفات UUID موثقة.
2. اختر ملف النشر من [`deployments/`](../deployments/README.md).
3. ضع الإعدادات والأسرار في مدير أسرار البيئة؛ لا تلتزم بها في Git.
4. ابدأ `PLATFORM_LICENSE_ENFORCEMENT=disabled` أثناء التهيئة فقط.
5. أنشئ المستخدمين بأقل صلاحيات واربط النطاقات والأدوار.
6. شغّل اختبارات الدخول والعزل وRLS بحسابين من مستأجرين مختلفين.
7. فعّل الهوية والنطاق بعد إثبات الملكية، إن كانت مشتراة.

### 7.2 إنشاء الترخيص

يعمل المثال التالي فقط من job خادمي معتمد يستخدم `service_role` مؤقتًا من مدير
الأسرار. يجب أن يكون `external_reference` فريدًا وقابلًا لإعادة المحاولة، مثل:

```text
ord_<order-number>_term_<YYYYMMDD>_<scope-id>
```

ولا يحتوي أي سر أو بيانات دفع.

```sql
select public.provision_commercial_license(
  target_tenant := '<tenant-uuid>',
  target_organization := null,
  target_facility := null,
  requested_model := 'trial',
  requested_status := 'trial',
  requested_hosting := 'cloud',
  requested_starts_at := '<UTC-start>',
  requested_expires_at := '<UTC-expiry>',
  requested_grace_ends_at := '<UTC-expiry>',
  requested_white_label := false,
  requested_modules := array['inventory','audit'],
  requested_max_users := 15,
  requested_max_facilities := 1,
  requested_external_reference := 'ord_<number>_term_<date>_<scope>'
);
```

تجربة `INV-RO-PILOT` تستخدم `trial` و90 يومًا ولا فترة سماح تلقائية. العقد
السنوي يستخدم `annual` و`active` وتاريخ نهاية سنة وفترة سماح 14 يومًا. إعادة
الطلب بالمرجع نفسه والشروط نفسها آمنة؛ تغيير الشروط مع المرجع نفسه يفشل مغلقًا.

### 7.3 التحويل إلى enforcement صارم

1. اقرأ ملخص الترخيص من حساب العميل وتأكد من الخطة والوحدات والنطاق والمدة.
2. غيّر `PLATFORM_LICENSE_ENFORCEMENT=strict` وأعد النشر.
3. اختبر أن الوحدة المشمولة تعمل من الخادم.
4. اختبر أن وحدة غير مشمولة تُرفض حتى لو عُرف رابطها.
5. اختبر حسابًا بلا صلاحية وحسابًا من مستأجر آخر.
6. اختبر العربية والإنجليزية وRTL/LTR والجوال.
7. سجل SHA والنشر والسيناريوهات والنتائج في تذكرة التهيئة.

لا يصبح الاشتراك `active` في سجل العمليات حتى تنجح هذه البوابة ويوقع مالك
القبول.

## 8. التجديد

### تجديد بنفس الوحدات والحدود

1. قبل 90 يومًا: راجع الاستخدام والدعم والنطاق والجاهزية والرصيد المستحق.
2. قبل 60 يومًا: أرسل عرض التجديد وبيان أي تغيير سعر.
3. بعد التوقيع/الدفع وفق العقد: احصل على `commercial_license_id` و`revision`
   الحاليين، ولا تستخدم قيمة قديمة.
4. حدّث تاريخ الانتهاء والسماح بتحويل optimistic:

```sql
select public.transition_commercial_license(
  target_license := '<license-uuid>',
  requested_status := 'active',
  requested_expires_at := '<new-expiry-utc>',
  requested_grace_ends_at := '<new-expiry-plus-14-days-utc>',
  expected_revision := <current-revision>
);
```

5. تحقق بحساب العميل وسجل revision الجديد ومرجع الفاتورة والقبول.

### تغيير وحدات أو حدود أو White Label

الدالة الحالية لا تعدل entitlements أو الحدود بعد الإنشاء. لذلك لا تعدل الجداول
مباشرة. أنشئ ترخيصًا بديلًا بمرجع طلب جديد، ثم نفذ في معاملة خادمية مراجعة:

1. provision للترخيص البديل كـ `draft` بالشروط الجديدة.
2. تحقق من الوحدات والنطاق والمدة.
3. في معاملة واحدة عند موعد القطع: ألغ القديم وحول البديل إلى `active` مع
   revision الصحيحين.
4. اختبر الوصول وسجل معرفي الترخيص.

قبل أتمتة هذه العملية يجب إضافة دالة استبدال ذرية واختبارات SQL؛ لا تجعل webhook
يكتب الجداول مباشرة.

## 9. عدم السداد والتعليق وإعادة التفعيل

1. النظام المالي يرسل حالة موثقة؛ لا تعتمد على رسالة موظف منفردة.
2. أرسل الإشعارات المتعاقد عليها وسجلها.
3. خلال السماح يبقى الترخيص `active` ويظل الوصول متاحًا حتى `grace_ends_at`.
4. بعد السماح، نفذ:

```sql
select public.transition_commercial_license(
  target_license := '<license-uuid>',
  requested_status := 'suspended',
  requested_expires_at := '<existing-expiry-utc>',
  requested_grace_ends_at := '<existing-grace-utc>',
  expected_revision := <current-revision>
);
```

5. تحقق أن Core فقط متاح وأن الوحدات محجوبة خادميًا، من دون حذف بيانات.
6. بعد تسوية المبلغ وموافقة المالية، أعد التفعيل بـ `active` وrevision الجديد،
   وحدّث التواريخ فقط إذا سمح العقد بذلك.
7. لا تمدد المدة لتعويض التعليق دون موافقة تجارية مكتوبة.

## 10. الإلغاء والانتهاء

1. تحقق من صاحب الطلب وشرط الإنهاء والتاريخ والمبالغ.
2. اتفق على نافذة تصدير البيانات وصيغته ومسؤوليته، عندما تصبح ميزة التصدير
   الإنتاجية متاحة؛ إلى ذلك الحين يكتب الإجراء اليدوي الآمن في SOW.
3. ألغ الوصول في الموعد بتحويل `cancelled`، أو استخدم `expired` للانتهاء الطبيعي.
4. ألغ الحسابات والتكاملات والمفاتيح والنطاقات حسب خطة offboarding.
5. لا تحذف قاعدة البيانات بسبب إلغاء الترخيص. طبق سياسة الاحتفاظ والحجز النظامي
   وطلبات الحذف المستقلة.
6. سجل محضر الإغلاق، ما أُعيد للعميل، وما بقي وسبب الاحتفاظ وموعد الإتلاف.

## 11. الترقية والتخفيض

- الزيادة أثناء المدة: تحسب نسبيًا بالأيام المتبقية، ولا تفعّل قبل نموذج طلب.
- التخفيض: يسري عند التجديد افتراضيًا، بعد التأكد أن الاستخدام الحالي ضمن الحد.
- نقل الترخيص من tenant إلى آخر ممنوع؛ أنشئ ترخيصًا جديدًا بعد مراجعة العزل.
- نقل المستخدمين أو البيانات بين العملاء ليس تغيير اشتراك عاديًا ويحتاج مشروع
  ترحيل ومراجعة خصوصية.
- لا يجوز لترخيص على مستوى منشأة أن يوسع الوصول خارج تلك المنشأة.

المعادلة النسبية:

```text
رسوم الزيادة = فرق MRR × الأيام المتبقية ÷ أيام دورة الفاتورة
```

## 12. White Label والنطاق المخصص

1. تأكد أن `white_label_enabled=true` في الترخيص النشط.
2. استلم دليل هوية يضم الأسماء العربية/الإنجليزية، ألوانًا صحيحة، أصول HTTPS،
   بريد تواصل، ورؤوس/تذييلات معتمدة.
3. افحص الملكية والحقوق في الشعار والأصول.
4. تحقق من ملكية النطاق عبر DNS قبل وضع `verified_at`.
5. اختبر الدخول قبل وبعده، metadata/favicon، العربية والإنجليزية، والتباين.
6. الهوية لا تسمح CSS/HTML/JavaScript مخصصًا ولا تتجاوز الصلاحيات.
7. عند الإلغاء أزل ربط النطاق بأمان؛ لا تعِد استخدام نطاق العميل أو أصوله.

راجع التفاصيل التقنية في
[White Label, deployment editions, and subscriptions](WHITE_LABEL_AND_LICENSING.md).

## 13. ما يجب بناؤه قبل الاشتراكات الآلية

الأساس الحالي يدعم الترخيص اليدوي الآمن، لكنه لا يجمع المال ولا يصدر فاتورة.
قبل البيع الذاتي أو التجديد الآلي يجب تنفيذ PRs مستقلة تشمل:

1. اختيار مزود دفع/فوترة يدعم النشاط والبلد والعملات والمتطلبات الضريبية.
2. جداول ربط غير حساسة بين customer/subscription/invoice والترخيص.
3. endpoint خادمي للـ webhook مع توقيع، منع replay، idempotency وسجل تدقيق.
4. آلة حالات تفصل `payment_pending` و`paid` و`past_due` و`refunded` عن license.
5. job مصالحة يومي بين المزود وقاعدة الترخيص وتنبيه للاختلافات.
6. دالة ذرية لتبديل خطة/وحدات/حدود الترخيص من دون نافذة وصول خاطئة.
7. prorations، credits، refunds، tax handling، وفشل الدفع وفق سياسة مكتوبة.
8. بوابة عميل للفواتير ووسيلة الدفع والإلغاء بعد مراجعة التفويض.
9. اختبارات sandbox وwebhook وترتيب الأحداث والتكرار والفشل والاسترداد.
10. مراجعة أمن وخصوصية وقانونية وضريبية واختبار قبول قبل Production.

حتى اكتمال ذلك: الفاتورة من النظام المالي، والتحصيل يتحقق بشريًا بفصل مهام،
والترخيص ينفذ من job خادمي معتمد فقط.

## 14. فصل المهام والمسؤوليات

| العمل | ينفذ | يعتمد |
| --- | --- | --- |
| تأهيل ونطاق وسعر | المبيعات/مالك المنتج | المسؤول التجاري |
| عقد وخصوصية | القانوني/الخصوصية | صاحب الصلاحية |
| فاتورة وتحصيل | المالية | مسؤول مالي مستقل |
| tenant وأدوار | عمليات المنصة | مسؤول أمن/منصة |
| provision/transition | job خادمي معتمد | تذكرة تحمل العقد والتحصيل |
| قبول العميل | نجاح العميل | مالك العملية لدى العميل |
| تعليق/إلغاء | عمليات المنصة | المالية + المرجع التعاقدي |

لا ينشئ الشخص نفسه العرض ويثبت الدفع ويفعل الترخيص بلا مراجعة مستقلة.

## 15. قوائم التحقق

### تفعيل

- [ ] العقد ونموذج الطلب متطابقان وموقعان.
- [ ] الضريبة والفاتورة والتحصيل موثقة.
- [ ] الخطة والوحدات في حالة تجارية مسموحة.
- [ ] tenant/org/facility صحيحة ولا توجد بيانات حقيقية في Pilot.
- [ ] الاستضافة والخصوصية والاحتفاظ معتمدة.
- [ ] الترخيص أنشئ بمرجع خارجي فريد ومن دون أسرار.
- [ ] strict enforcement مفعل في البيئة المقصودة.
- [ ] اختبار مشمول/غير مشمول، صلاحيات، RLS وعزل مستأجرين ناجح.
- [ ] الهوية والنطاق مختبران إن كانا مشمولين.
- [ ] قبول العميل، SHA، رابط النشر، والنتائج محفوظة.

### تجديد

- [ ] إشعارات 90/60/30 يومًا.
- [ ] مراجعة الاستخدام والحوادث والدعم والنطاق.
- [ ] عرض وتجديد وتحصيل موثقان.
- [ ] revision حديث قبل الانتقال.
- [ ] التواريخ والسماح بالتوقيت UTC.
- [ ] اختبار بعد التجديد وتحديث السجل.

### إغلاق

- [ ] صاحب الطلب وحق الإنهاء متحققان.

## 16. خطة التنفيذ التجارية لأول 90 يومًا

### الأيام 1–14

- اعتماد هذا الدليل وأسعار القائمة وسلطة الخصم.
- اختيار نموذج عقد وNDA وDPA وSOW ونموذج طلب بمراجعة مختصة.
- اختيار نظام CRM/سجل مقيد ونظام فوترة متوافق.
- تحديد مالكي المبيعات والمالية والخصوصية وعمليات المنصة والدعم.
- إنشاء بيئة Demo ثابتة ببيانات خيالية وسيناريو Inventory Read-Only.

### الأيام 15–30

- استهداف 10 عملاء مناسبين للتجربة، وتنفيذ 5 جلسات اكتشاف.
- بيع تجربة واحدة فقط أولًا لتثبيت التهيئة والدعم والتكلفة.
- قياس ساعات العمل الفعلية ومراجعة سعر 18,000 ريال قبل التجربة الثانية.

### الأيام 31–60

- إكمال التجربة الأولى واختبار القبول والحصول على مرجع قابل للنشر بعد الموافقة.
- بناء backlog GA من الفجوات الفعلية، لا من العروض الافتراضية.
- بدء billing adapter في نطاق مستقل بعد اختيار المزود والمراجعات.

### الأيام 61–90

- قرار go/no-go لبيع تجربة ثانية.
- تحديث مصفوفة الجاهزية والأسعار والهامش والمواد البيعية.
- لا فتح اشتراك إنتاجي حتى توقيع بوابة GA للأمن والتشغيل والدعم والوظائف.
